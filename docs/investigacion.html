Resumen ejecutivo

Se propone React/Vite en Vercel, Express en Render y PostgreSQL gestionado por Supabase. El navegador hablará con /api en el mismo origen; Vercel reenviará las solicitudes a Render. Las cuentas, permisos y sesiones serán responsabilidad de Express. Supabase almacena datos: no ejecuta nuestro servidor Express. El acceso, los planes, el dominio y los resultados reales aún deben comprobarse en las cuentas del equipo [1–4].

Navegador ⇄ HTTPS ⇄ Vercel (React y reescritura /api) ⇄ HTTPS ⇄ Render (Express) ⇄ TLS ⇄ Supabase (PostgreSQL)

1. Modelos de alojamiento

PaaS administra despliegue y parte de la operación; reduce mantenimiento y control del sistema, con límites y precio por plan. Un VPS/IaaS entrega infraestructura virtual: más control sobre sistema y red, pero el equipo actualiza, protege y supervisa el servidor. Un contenedor empaqueta aplicación y dependencias; no es por sí solo un servidor ni una tarifa: puede ejecutarse tanto en un PaaS como en un VPS. La factura depende de recursos y uso; no existe un ganador universal.

2. Papel de Supabase y elección

Supabase Free anuncia $0, hasta dos proyectos activos y 500 MB de base por proyecto; los proyectos gratuitos pueden pausarse después de una semana de poca actividad [3]. Ofrece PostgreSQL gestionado, no un proceso Express. Elegimos Render por el servicio web Node, Vercel por el frontend Vite y Supabase por PostgreSQL, como pide el laboratorio. Render Free no se recomienda para producción real; la pausa y el límite de horas pueden afectar la evaluación. Vercel Hobby restringe el uso a proyectos personales no comerciales; la compatibilidad con el repositorio y la colaboración del equipo debe comprobarse en el panel [1–3].

3. Secretos

En producción se introducen en el gestor de variables o secretos del proveedor, con acceso mínimo, separación por entorno y rotación. Un archivo .env facilita desarrollo, pero no protege de copias, filtraciones o acceso al disco; se excluye de Git. Nunca se incorporan secretos al frontend ni a variables VITE_. La llave de datos y el secreto de sesiones son distintos.

4. TLS, certificados y HSTS

TLS cifra y protege la integridad del transporte; el certificado permite validar la identidad del servidor mediante una cadena confiable y el nombre de dominio. Let's Encrypt es una autoridad certificadora que valida el control del dominio y automatiza emisión y renovación con ACME [9]. HSTS indica al navegador que vuelva a usar HTTPS para ese host; no protege una primera visita HTTP previa al aprendizaje de la política, salvo que corresponda una lista precargada [10].

5. Proxy inverso y confianza

Un proxy inverso recibe solicitudes y las dirige al servicio interno; puede terminar TLS, aplicar reglas y distribuir tráfico. Nginx y Caddy son ejemplos. Express puede necesitar trust proxy para interpretar IP y protocolo reenviados. Debe configurarse según la topología real y las cabeceras que el último proxy sobrescribe: confiar en todo o copiar una cantidad de saltos sin verificar permite falsificar datos [11]. La ruta directa de Render también debe evaluarse.

6. Procesos y reinicios

PM2 o systemd supervisan un proceso en un servidor propio y ayudan a reiniciarlo. En un PaaS, la plataforma ya administra el ciclo de vida de la instancia; no se añade otro supervisor sin necesidad. La aplicación debe cerrar ordenadamente y no depender del disco efímero [1, 4].

7. CI/CD mínimo

GitHub Actions selecciona Node LTS, ejecuta npm ci, pruebas contra PostgreSQL de pruebas, auditoría de dependencias y compilación de React. Solo se promueve el commit que pasó CI; desactivar o condicionar el autodespliegue en los paneles evita una carrera. No se exponen secretos de producción a pruebas de pull requests [12]. La ejecución real queda pendiente hasta disponer de repositorio y configuración.

8. Bases gestionadas y conexión

Entre las opciones están Supabase PostgreSQL, Render Postgres y Cloud SQL [1, 3, 13]. Para Express persistente, Supabase recomienda conexión directa cuando la red la admite, o pooler de sesión cuando se necesita IPv4 [14]. Usar TLS con validación de certificado y nombre, rol de aplicación de privilegios mínimos, credenciales separadas para migración, límites de conexiones y respaldos. No desactivar la validación del certificado para solucionar errores. Revisar la exposición de la Data API y no alterar globalmente un proyecto compartido sin evaluar el impacto.

9. De desarrollo a producción

En producción: cookie de sesión HttpOnly, Secure, SameSite=Lax y sin Domain; CSRF ligado a sesión y validación de origen; CORS solo para orígenes exactos cuando haga falta; logs JSON sin datos privados y errores públicos genéricos. NODE_ENV=production habilita el comportamiento de producción, pero no sustituye estos controles. La conexión de datos, las llaves y los orígenes se configuran por entorno. No enviar el dato completo al navegador para ocultarlo después.

10. Comprobaciones posteriores al despliegue

Con datos ficticios del equipo: comprobar HTTPS, redirección, certificado y HSTS (SSL Labs); cabeceras del HTML y API (SecurityHeaders); navegación y cookie en el navegador; registro, recarga, aislamiento entre usuarios, CSRF, límite de login, correo de recuperación y cierre efectivo. Verificar el cifrado en filas saneadas, conectividad TLS a PostgreSQL, logs sin secretos y estado de salud. Ejecutar auditorías npm y ZAP baseline solo contra la aplicación propia. Registrar dominio, fecha, commit, resultado y límites de cada prueba. Estas comprobaciones son un plan, no resultados de producción.

Plan justificado

Primero diseñar permisos, datos, amenazas y contrato; luego implementar cada recorrido con pruebas de integración sobre una base desechable. Después configurar migraciones y roles separados, preparar CI y despliegue condicionado. Finalmente ejecutar los recorridos y reportes reales en el dominio propio. Mantener separadas la evidencia local, la pública y las tareas que dependan de cuentas. El texto cifrado en la base reduce la exposición de un volcado; Express puede descifrar después de autorizar, por lo que no es cifrado de extremo a extremo.

Advertencias de la comparación

Cloud Run cobra consumo adicional y servicios asociados; debe revisarse la cuenta de facturación antes de usarlo. Los límites exactos de duración de Vercel dependen de su configuración y la documentación consultada presenta cifras distintas; no se fija aquí una cifra única [2, 6]. La disponibilidad de funciones y de una integración Git depende del plan y de la cuenta real.
